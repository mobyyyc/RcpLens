## Backup behavior

Settings offers **Export encrypted backup** and **Restore from backup**, using native Forms and Files pickers. Export requires a user-chosen password (at least 12 characters, at most 1,024 UTF-8 bytes) and confirmation. The password is never saved in preferences, Keychain, SQLite or the archive. Forgotten passwords cannot be recovered. Choose a long unique password and keep it separately from the file.

The backup covers every saved receipt (including drafts and archived/starred receipts), exact encoded originals, original OCR/parser evidence, all correction revisions, raw review input/guidance checks and split participants/assignments/policies/finalization. Paper/swipe wallet preferences are included for completeness. Device storage keys, Face ID/passcode settings and app-lock delays are excluded. **Merge keeps local wallet and security preferences**; it adds missing receipts without applying exported preferences.

Restore accepts exactly one explicitly selected file. It coordinates access and copies only its encrypted bytes in bounded chunks, then authenticates and validates it into a fresh isolated encrypted SQLite store using a random temporary key. No plaintext receipt/image file is created. The preview gives total/new/skipped/conflict counts. Existing receipt IDs always win, including differing revisions; no record is replaced. A new receipt whose asset ID collides with an existing asset stops the entire restore. Duplicate receipt or asset ownership within an archive is invalid. After explicit confirmation, all new records/assets are re-encrypted under the receiving device key in a single SQLite transaction. A changed preview requires selection/review again. Restore does not run OCR, re-encode originals or recreate revisions.

The Files picker coordinator captures the temporary password and workspace session ID at presentation. It disposes of the password after selection/cancel; an unselected secret releases with the coordinator after native dismissal. Results from an old locked/backgrounded session are ignored. Export results and presentation dismissal also require the captured session and matching encrypted file URL. Native save can dismiss before its delegate; separate presentation state retains the file until delegate completion or final coordinator release after a swipe. Close/cancellation revokes a dedicated operation permit. Checks precede expensive work, each copy/frame/receipt and commit. The commit boundary shares the existing synchronous revocation lock. A cancellation after commit cannot undo receipts; the wallet refreshes after the actor finishes. Background/protected-data loss drops prepared references, clears presentation/password state and closes the store. Transient Files/Face ID inactivity retains the session behind the existing privacy cover. Swift strings/CryptoKit internals cannot promise complete forensic memory erasure; password state/references are discarded and the mutable KDF input/output Data buffers are reset as practical.

Archives are limited to 1,000 receipts and 256 MiB. Each record is at most 8 MiB and each original at most 32 MiB; manifest is at most 16 KiB. Semantic limits include 10,000 lines/OCR observations/issues/checks, 1,000 revisions, 2 MiB parser output/review input, existing image dimension limits and exact-money/split validation. Review input must decode, preserve matching revision fields and meet the saved draft/source-review gate; legacy nil review input remains valid. Timestamps must be representable. Unexpected formats, unsupported versions, malformed lengths, wrong passwords, damaged/truncated/reordered/trailing frames and unsupported data fail before production writes. Limits intentionally bound personal-device work; larger wallets need a separately reviewed format expansion.

## Portable format v1

The file extension is `.slipletbackup`. Binary header: 12 ASCII bytes `SLIPLETBK001`, followed by a fresh 16-byte random salt. Version 1 fixes PBKDF2-HMAC-SHA256 at 600,000 iterations and a 32-byte derived key; no attacker-controlled iteration count exists. Each frame has a 4-byte unsigned big-endian ciphertext length, then CryptoKit AES-256-GCM combined bytes (12-byte random nonce, ciphertext, 16-byte tag). Authenticated additional data is the exact 28-byte header followed by the frame index as an unsigned 64-bit big-endian number, starting at zero.

Frame zero is encrypted JSON `ReceiptBackupManifest` (version, current store schema, creation time, receipt count, wallet preferences). For each receipt in sorted receipt-ID order there is an encrypted ReceiptRecord JSON frame and an encrypted original-image frame. The authenticated count fixes the number of frames; any trailing byte fails. Frame indices prevent reorder/duplication, tags protect contents/header and count prevents truncation. No ZIP/compression/path extraction is used. Only the magic/salt/frame sizes are public; merchant, receipt IDs, revisions and counts are encrypted. Backup format version must increase for incompatible/otherwise silently lost future record fields. This is portable protection independent of the non-synchronizing, device-bound storage Keychain key.

Encrypted task exports/staging stores use complete file protection, restrictive permissions and excluded temporary directories. They are deleted on cancellation/error/completion when references release. An abrupt process termination may leave encrypted task-owned temporary files; their temporary keys are not persisted. The OS manages temporary-directory reclamation. Do not claim crash-proof immediate deletion or physical file-protection enforcement from Simulator checks.

## Repeatable personal-phone protocol

Use the same stable bundle, local directory and Keychain service/account; retain the existing Personal Team signing settings. Install updates over the app, never uninstall for an upgrade check. Before any phone upgrade, record receipt/draft/archived/starred counts and a few exact split totals; create a password backup through Files, then prove restore using a separate fictional/isolated store before relying on it. Main/user must explicitly select a phone destination; this task installs nothing on a phone or a normal Simulator.

1. **Upgrade and backup:** photograph/export originals and note receipt revision history, draft guidance checks, stars/archive and split choices before upgrade. Upgrade without deleting the app. Reopen and compare. Export to an explicit local Files folder; cancel export once; choose/cancel restore once; test a wrong password and damaged *fictional* archive. Preview a duplicate/differing receipt and confirm existing edits stay. Keep an independent restorable backup before deleting anything.
2. **Offline shopping:** use airplane mode and capture/import one No Frills, Costco and T&T receipt across repeated actual shopping sessions (at least two per store). Keep original phone photos private. Include normal, long and poor photos; source compare dates, quantities, every price, discounts/taxes/deposits and printed total. Do not treat a matching total as full accuracy. Capture/import/review/save/search/split must work without Apple Intelligence.
3. **Timing:** record purchase-level groups, store, image conditions, phone/OS, capture/import-to-review latency, correction edits and human review-to-save time. Report median and slow cases with denominators, omissions/extra lines and each store separately. Keep an untouched held-out set and independently checked originals; a phone photo and flat scan of one purchase are one group.
4. **Lifecycle/privacy:** interrupt recognition, backup preparation/export and confirmed restore with background/lock; return after unlocking. Verify no private app-switcher preview, cleared passwords, no ghost saves and a usable wallet. Cancel Face ID, fail once, use passcode fallback, test immediate and chosen grace delays. Simulator fixture checks do not measure real Face ID or hardware file protection.
5. **Review and originals:** check long-receipt bottom access and zoom, mixed-language text, source boxes/alignment, focused Cancel/Apply, large text/VoiceOver and Reduce Motion. Retest the P2-04 immediate **Split Done → Edit** flow and retained invalid-frame/priority warnings on the actual phone; do not dismiss warnings solely as driver effects.
6. **History and exact splits:** find a new/restored receipt by merchant/item/month, include archived items, reopen drafts with guidance checks, assign purchases, review adjustment policies and finalize. Independently add participant cents to the receipt total (odd-cent/discount case included). Reopen after restart. Edit a finalized receipt and verify split finalization is invalidated and drafts cannot finalize.

For every session record pass/fail/pending, actual dates and observed times, interruption point, and relevant app/OS build. Keep images/OCR/labels and participant identities private and ignored; public reports contain aggregate counts/limits only.

## Release status

Eight distinct native cases are covered across a six-pass full run and scoped final picker/session/export runs (four and two passes); the initial full unit suite passed 139 with one hardware-only skip, and 14 focused backup/migration cases passed after implementation refinements. Original earlier failures and the corrected callback-ordering issues remain recorded rather than counted as final passes. An actual encrypted local Files save/explicit selection to duplicate preview and byte-identical three-receipt in-place 0.1→0.2 upgrade passed on disposable Simulators. These do not certify external phone providers or physical-device behavior.

Native automated results and exact paths/hashes are recorded in [P2-05 validation](evidence/p2-05/validation.json). The physical-phone protocol is **pending**, including real Files-provider completion, camera/offline airplane-mode sessions, Face ID/passcode, hardware data protection, source alignment/accessibility, warning investigation, phone processing latency and human correction effort/time. Historical positive phone feedback does not replace these checks.

The accepted recognition baseline remains 57/66 exact purchase amounts on five exposed development purchases, with zero held-out purchases. This task changes no recognition/parser code. The proposed ≥95% purchase recovery, ≥90% merchant/date/printed-total accuracy and median correction time <30 seconds are **unmet/unmeasured release targets**, not achieved claims. A personal build can be prepared for testing, but release measurements remain open.
